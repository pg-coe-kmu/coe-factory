**Ziel:** Eindeutige natürliche Antworten landen im richtigen Feld mit dem richtigen Wert; Unsicheres führt zu einer Nachfrage in der Antwortform des Felds, nie zu einem geratenen Wert. Gemessen wird das mit einem Antwortkatalog (Test ohne KI) und einem Prüfwerkzeug (echte KI).

**Architektur:** (1) Jeder `Feldtyp` beschreibt seine Antwortform. (2) `AUSWAHL` vergleicht über einen Schlüssel und kennt Namen und Synonyme; „?“ legt nichts fest. (3) Die Extraktions-KI bekommt die gestellte Frage und die Antwortform (ein gemeinsamer Prompt-Helfer für alle drei Adapter), die Nachfrage bittet in der Antwortform. (4) Erst danach lesen die Normalisierer keine Zahlen mehr aus Sätzen. (5) Katalog-Test, (6) Werkzeug unter `werkzeuge/`, (7) Läufe und Bericht.

**Technik:** Python 3.11+, Standardbibliothek, pytest, Test-KI `FakeLLM`; Werkzeug-Läufe mit `GeminiLLM` (`gemini-3.8-flash`, `BC1_LLM=gemini`).

**Spec:** `design/Spec-Antwortformen.md` (Entwurf 3, abgenommen; Abschnitt 9 = Reihenfolge und Haltepunkte, Abschnitt 13 = Rulings). Änderungen aus der laufenden Nachprüfung der Spec werden vor dem Bau eingearbeitet.

## Globale Vorgaben

- **TDD-Guard nie umgehen.** `*.py` unter `coe-factory/` NUR mit Edit/Write/MultiEdit ändern; Bash nur für pytest, git und Messungen (wer per Bash schreibt, umgeht den Guard). Je Edit genau **eine neue Testfunktion** (Parametrisierung innerhalb einer Funktion ist erlaubt). Nach jedem Edit voller Lauf `.venv/bin/pytest` aus `bc1-context-discovery/`. Bei jedem Block das Skill `tdd-guard` aufrufen; neue Blöcke dort eintragen. Nach jedem Task die Werkzeugaufrufe des Subagenten auf Bash-Schreibzugriffe prüfen.
- **Kette bei jedem neuen Merkmal/Helfer** (Lessons „Hilfsfunktion vor ihrem Aufrufer“, „kleinere Schritte“): (1) Aufrufer mit Literal/neuem Namen → pytest (NameError/TypeError ist der RED); (2) Stub mit Rückgabe (`return None`, `return ""`; **kein** `raise`-Stub) → Assertion-RED; (3) Logik; erst bei grüner Suite zu Konstante/Schleife verallgemeinern. Umbauten nie im roten Schritt beginnen.
- **Bestandstests ändern in zwei Schritten:** erst nur Aufruf/Argument nachziehen, die geänderte **Erwartung** erst, wenn der Test nur noch an dieser Assertion rot ist. Zusätzliche Assertions in grünen Bestandstests werden vom Guard abgewiesen → eigener neuer Test.
- **Test-Fakes** (Hilfsklassen in Testdateien) bekommen Attribute/Methoden erst, wenn ein Test sie verlangt; Fakes hinter der API meiden (echter Writer, Skill-Lesson).
- **Mutationsprobe** für jeden bei Ankunft grünen Test: Projekt in den Scratchpad kopieren (`cp -R bc1_core bc1_service werkzeuge tests pyproject.toml <scratchpad>/mut/`), dort mit Edit mutieren, `cd <scratchpad>/mut && ../…/.venv/bin/python -m pytest tests/<datei> -p no:cacheprovider -p no:tdd-guard` — Test muss rot werden. Im Bericht festhalten. Nie im Repo mutieren, kein `git checkout` auf uncommittetem Stand. Reine Prüfläufe (`--co`, `--trace-config`) immer mit `-p no:tdd-guard -p no:cacheprovider`.
- **Geschütztes Leerzeichen/Sonderzeichen** nie literal in Regex tippen (` `); Edit-Anker nicht mit Leerzeichen am Ende; vor jedem Commit `git diff` lesen.
- **Generische Testdaten** (Repo ist öffentlich): Namen wie „Auftrag-Abwicklung“, „Vertrieb & Innendienst“, „Lager+Versand“, „Geschäftsführung“, „Anfrage erfassen“; keine Namen aus der Generalprobe, keine Personen. **Erwartete Werte sind Strings** (`"180"`).
